二、必须处理的问题（按优先级）
P0
发布通道断裂：测试人员拿不到 0.5.7
lan-update/version.json 仍为 versionCode:22 / v0.4.3；lan-update/ 目录里最新 APK 是 surf-reader-0.4.3.apk，没有任何 0.5.x 包体；GitHub 也仅发布到 v0.4.3。 自动更新靠比对 versionCode > 本地，而服务器播的是 22 < 35，因此客户端**不会收到任何 0.5.x 更新**。
建议：构建 0.5.7 APK → 更新 version.json 指向 code 35、apkUrl: surf-reader-0.5.7.apk → 放入 lan-update → 建 GitHub Release 挂包体（沿用既有约定）。
P1
包体膨胀：13.3MB 死资源
实测 0.5.7 APK = 33.1MB（0.4.3 为 18.7MB）。assets/art/ 占 13.3MB / 12 个 PNG，但代码里仅引用 character/avatar_circle.png 一处（设置页小鲸头像）。 bg_deep_ocean.png、bg_splash.png、多数 character_*.png、whale_tail_only.png、splash_celebrate.png 在源码中无任何引用；WhaleBackground 是纯 Compose 渐变绘制，不读任何 PNG。
建议：删除上述未引用素材，APK 可回落至 ~20MB，安装体积与首包下载减半。
P1
调试日志泄漏到 release 包
resolveCoverUrl() 每次解析封面都会无条件调用 logCoverToFile()（反射拿 Context 写 cover_debug.txt）。该逻辑无 BuildConfig.DEBUG 守门，因此在 release 包中每个封面加载都伴随一次文件 I/O，是持续无意义开销。
建议：用 if (BuildConfig.DEBUG) logCoverToFile(...) 包起来，release 彻底关闭。
P2
版本号历史分叉
git 历史里存在一个 v0.6.0 提交（versionCode 31，Aug 15 12:56，含一批美术素材与 ANIBUZZ 框架文档），却排在当前 v0.5.7（code 35）之前。即版本名曾升到 0.6.0 又被回退到 0.5.x 续号。 因自动更新只认 versionCode（35 单调递增），功能不受影响；但 git 历史出现一条“废弃的 0.6.0 线”，易误导。
建议：明确该提交已废弃（或加注释），避免后续误以为是正式版本。
P2
文档与规划文件堆积、过期
知识库-冲浪阅读项目.md 头部仍写“适用版本 v0.4.3”；README.md 停留在 M1–M3 表述。 根目录堆积 8 份规划/设计文档（ANIBUZZ-FRAMEWORK-DESIGN.md、VISUAL-SPEC-v2.0.md、PHASE1/PHASE2-OVERVIEW.md、PLAN-0.4.0.md、ROADMAP.md、TOPBAR-POSTMORTEM.md、M2.5-PLAN.md），部分已与现状脱节；AssetImage.kt 文件定义的函数实际叫 ArtImage（命名不一致）。
建议：过期规划文档归档或删除；知识库/README 刷新到 0.5.7；补打 git tag v0.5.7（目前仅 v0.2.8 一个 tag）。
